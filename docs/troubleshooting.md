# 故障排查

## 没有收到邮件

1. 执行 `python -m tibo_mailer doctor`。通过只表示格式正确，不代表邮箱登录或网络已验证。
2. 执行 `python -m tibo_mailer test-email`，检查收件箱和垃圾邮件。确认邮箱已开启 SMTP，授权码有效，主机与端口符合服务商要求。
3. 执行 `python -m tibo_mailer status` 查看 `health` 和投递状态。不要把整个 SQLite 数据库上传 Issue。
4. 程序只接受明确的重置信息，普通推文不会发邮件。规则模式可能漏掉复杂语义，可以配置自己的模型 API 改用 `llm`。

## X 读取失败

`source_ok: false` 表示本轮没有成功完成来源/分析检查，不能解读为没有新公告。运行 `check --dry-run` 查看是否能得到当前的本人帖子；注意本轮若模型分析失败也会记录失败类型。服务可能限制匿名访问，页面结构也可能变化。

原帖线程单独失败时记录 `warnings`，对应证据保留到下一轮，不凭不完整内容发送。程序不通过搜索缓存、Nitter 或第三方代理替代 X，也不会索要 X Token。确认你的运行环境能够正常访问官方 X 页面。

## 模型失败

`ANALYSIS_MODE=llm` 需要你有权限使用的模型、HTTPS 接口和 API Key。接口必须支持 Chat Completions JSON 模式。请求异常、无效 JSON 或原文引用校验失败时不会标记帖子已读，也不会默默降级成另一个模型。

默认 `rules` 不请求模型接口，摘要使用固定中文模板；它对模糊表述更保守。

## 邮件结果不明确

`unknown` 代表邮件可能已经发出，程序不会自动再发。先在发信账号的已发送记录或邮件服务日志中查找记录的 `Message-ID` / 主题 / 原帖 ID，再使用 README 中的 `resolve` 命令处理。

部分 SMTP 服务不会把通过 SMTP 提交的邮件存入“已发送”文件夹。此时以服务商投递日志和收件箱记录核对；没有证据时保留 unknown，避免重复。仅服务器接受 DATA 的成功状态叫 `sent`，不保证收件箱投递。

## 重启后重复首次汇总

检查工作目录和 `TIBO_DATA_DIR` 是否改变、数据库或 Docker 命名卷是否被清理。保持一份持久状态，不要将 `.env`、数据库复制给其他用户。若迁移服务器，停止旧实例，整体迁移私有数据目录后再启动。

## 时间看起来差了一小时

检查原文使用 PST、PDT 还是 PT。夏季洛杉矶通常使用 PDT，但作者仍可能写 PST。程序保留字面解释，并显示未经确认的当地时间备选；不能把两个解释中较早的一个当作确定时刻。

## 长期运行建议

服务器使用 Docker Compose 的重启策略；定期检查 `status` 中的最近检查时间与 warnings。首版通过本地日志和状态提供故障可见性，不提供独立的外部存活监控。电脑睡眠、程序退出、源站失败都可能延迟提醒。
